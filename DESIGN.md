# moth2 design

Rust/WebAssembly rethink of [the C++ version of moth](https://github.com/arnaud-sintes/moth/tree/cpp-final) (this repository's history up to the tag `cpp-final`): a lightweight OOP framework with a WPF/Qt-style parent/child component tree for the browser, direct DOM binding (no virtual DOM), and reliable destructors. This is the design and verification record; to *use* the framework start with the [README](README.md).

**Target: Chromium (Chrome, Edge) only, by decision.** Firefox and Safari are out of scope, so the code uses Chromium's platform freely (constructable stylesheets, `ElementInternals`, `delegatesFocus`, `static` class fields, `:has()`...) and nothing here is checked against other engines. All browser tests and end-to-end runs use headless Edge.

## Decisions

| Topic | Decision |
|---|---|
| Language / target | Rust, `wasm32-unknown-unknown` |
| Bindings | `wasm-bindgen` + `web-sys` (no emscripten) |
| Element creation | Rust-created elements (Rust owns the element); markup-created elements as an opt-in second mode (the DOM owns the element, Rust owns the component) |
| Layout | one `moth` library crate (serde only behind the optional `replication` feature); samples: `front-end` (image streaming), `todo` (replication) and `viewer` (server-rendered 3D), all trunk; `back-end` (axum, native); `protocol` (serde messages, the todo model and the viewer's wire format, shared by both sides); `render` (a pure CPU rasterizer and JPEG encoder, native only) |
| Build | `trunk` (`cargo install trunk --locked`), tests via `wasm-bindgen-test` in a real browser |
| Web platform | custom elements, Shadow DOM, `<template>`, constructable stylesheets, `<slot>`, `::part()`, `ElementInternals`, `ResizeObserver`, `matchMedia` |

## Acceptance criterion

moth's core promise (proper destructors, nothing dangling) was never delivered by the C++ version; see [its audit](docs/audit-of-the-cpp-version.md). The failure modes that exist in Rust have tests: dangling parent/child and id lookups (`lifecycle.rs`), callbacks outliving their owner and the silent send failure (`lifecycle.rs`, `websocket.rs`), the broken container erase (`children.rs`). The others disappear by construction and have nothing to test: the comma-joined serializer and the `Data<T>` template (replaced by serde), the compiler-locked `Ctti` and the variadic macros (replaced by derive).

What is and is not guaranteed:

- **Memory safety by construction:** no `unsafe` in the library or the samples (the `unsafe extern` block that imports the JS shim is syntax edition 2024 requires).
- **No use-after-drop:** a dropped component's listeners, frame callbacks and socket handlers are unregistered and are not called again, even for events that were queued while a callback was running. This is tested and, for the paths listed under "How the tests were checked", mutation-checked: removing the unregistration makes the corresponding test fail.
- **Leak-freedom is not guaranteed, only made easy.** A callback that captures its owner (instead of a weak handle) creates an `Rc` cycle, and nothing stops it; `Prop::bind` bindings last as long as the prop (use `bind_scoped` for shorter-lived components); `mount` and markup-created components rely on `pagehide` for teardown.

## Ownership model

- **Rust owns everything; the DOM is a view.** `Drop` is the single teardown path: it removes the host element and unregisters listeners.
- **Node references, not ids.** Components keep their `HtmlElement`, never a string id to look up. `remove()` is idempotent, so a child dropped after its parent's DOM is gone is a no-op (fixes the audit's `getElementById(...).remove()` TypeError).
- **Listeners own their closures** (`Listener` is an RAII guard). Once it is dropped its callback is not called again, including for events queued while the callback was running (a flag shared with the dispatcher).
- **Callbacks never capture the owner.** They capture a non-owning handle (`label.text_handle()`, `SocketHandle`, `SliderHandle`...); if the owner is gone the callback is a no-op (fixes the raw `this` capture).
- **No lifetime-parameterized children** (`Label<'p>`): a page struct holding `body` and a `label` that borrows it is self-referential and does not compile, and that struct is exactly moth's idiom.
- **Parents.** Constructors take a `&impl Parent`: any component, or an `ElementRef` (an inert, non-owning reference to an existing element, which adds nothing to it). `Anchor` additionally gives an adopted element the `enabled` property; do not wrap an element that already has a component (both would own its `disabled` state).
- Static children are struct fields. Dynamic children go in `Children<T>` (generational keys: a stale key returns `None`) or, for a list that mirrors a model, `Keyed`.
- Rust drops struct fields in declaration order (C++ is reverse). This is safe because of the points above and is covered by tests.
- Destructors do not run on tab close. `moth::mount(root)` keeps the root alive and drops it on `pagehide`, together with every markup-created component. A `pagehide` with `persisted` set means the page goes into the back/forward cache and may come back, so nothing is dropped then; a restored page keeps its DOM but its sockets are gone. A `Link` with reconnection enabled reconnects at once on such a `pageshow` (checked with a synthetic event; a real bfcache restore was not observed, nor whether the browser would even admit a page that held an open socket), the plain `WebSocket` does not.
- `Drop` never panics; failures during teardown are swallowed. Constructors return `Result<_, moth::Error>`; moth never panics on a DOM failure (a wasm panic aborts the whole app).

## Web Components layer

- The one hand-written JS file is `moth/src/shim.js` (56 lines, 43 of code): `define_element(tag, template, css, attributes, formAssociated)` defines a generic custom element class, because wasm-bindgen cannot define a class extending `HTMLElement`. The class attaches the shadow root (`delegatesFocus`) and `ElementInternals`, observes the declared attributes, and forwards `connected` / `disconnected` / `attribute` to one Rust hook. It is idempotent for moth's own classes and an error for a tag something else already defined; it is never edited when adding components.
- A component type is a `Definition` (tag, shadow template, stylesheet, observed attributes, form-associated flag); stock ones are `elements/<name>.html` + `<name>.css` + a Rust type. The template is parsed once per tag and `cloneNode`d per instance; the stylesheet is one constructable `CSSStyleSheet` shared through `adoptedStyleSheets`.
- Parent/child composition = light-DOM children projected through `<slot>`.
- Theming from outside: CSS custom properties (`--moth-button-*`, `--moth-input-*`, `--moth-accent`, `--moth-panel-*`, `--moth-canvas-height`) and `::part()`. Global stylesheets cannot reach inside shadow roots; a light-DOM opt-out is not built.
- Not done: `:state()` custom states instead of the `toggled` attribute, form `reset` / validity callbacks.

## Events: child to parent

A child tells whoever contains it, without knowing who, with a DOM event rather than a closure it was given:

- `emit_from(target, name, detail)` / `Component::emit` / `ElementRef::emit` dispatch a `CustomEvent` that **bubbles and is composed**. Composed is what lets one raised from inside a component's shadow root reach ancestors and page scripts, with `target` retargeted to the host; a test dispatches the same event non-composed from inside a shadow root as a control and shows it stays inside. `Component::on` / `ElementRef::on` listen on an element, for its own events and for those bubbling up from inside it, until the returned `Listener` is dropped. `event_detail` reads the payload.
- The stock components raise `events::TOGGLE` (a `ToggleButton` clicked while enabled; `detail` is the state after the click, or for a `controlled` one the state it asks for) and `events::SELECT` (a `Dropdown` choice; the index, or `null`). Not for programmatic changes. They are not raised for what the platform already gives: `click` and `input` are composed, but `change` is not, hence `SELECT`.
- The toggle event is raised *before* the user callback, so ancestors see the button still attached if the callback removes it (tested). A parent handler may drop the child that is raising an event.
- Parents are still free to use closures and weak handles; events are the decoupled option, and the only one a markup page can use.

## Declarative components (markup-created elements)

`moth::define_all()` makes the stock elements usable in markup (`<moth-label text="..">`, `<moth-toggle-button toggled>`, `<moth-slider min max value>`, `<moth-edit name value>`, `<moth-panel>`...); `moth::define::<T: Declarative>()` does the same for a user component. Rust owns the component, the DOM owns the element:

- the component is created when its element first connects, then told the attributes it already has (in the order of `Definition::attributes`, so a range comes before the value clamped against it). Elements already in the page when the tag is registered are upgraded at that moment, whatever order tags and Rust constructors were defined in;
- the id that marks "has a component" is set *before* the component is built, so a component that reconnects its own element while attaching does not trigger a second instance;
- a tag belongs to one component type: registering another type under it is an error;
- attribute changes are reported to it; `disabled` is the host's business (see "Enabled");
- it is dropped when its element is disconnected for good. Moving an element disconnects and reconnects it within one task, so the hook checks `isConnected` in a microtask and a move keeps the component; the component is also dropped on `pagehide`;
- an element connected again afterwards gets a fresh component; the previous state is gone;
- elements created by Rust are marked (`mothOwned`) and never instantiated a second time.

A user component builds Rust-owned children inside the element it is given (a `Host` is a `Component`, so it can be a parent) and they are dropped with it. In markup there is no Rust callback: stock elements are driven by attributes, and their events are ordinary DOM events (`click`, the composed `input`, tested on the host). Text components in markup treat their content as the text: the first change of the `text` attribute replaces all of it.

**Reaching what the page declared.** `Declarative::of(&element)` (also `ElementRef::declared::<T>()`) returns a `Declared<T>`: typed, non-owning access to the component of a markup element, through `with(|c| ...)`. The DOM owns the lifetime, so `with` returns `None` once the element is gone, while the component stays alive for the duration of a `with` call even if the closure removes its element. It returns `None` for an element of another type, a plain element, an element not yet connected, and an element Rust created (its owner already has the component). For an element with no component of its own, `ElementRef::on(event, handler)` gives behaviour that lives as long as the returned `Listener`, which is how a plain `<button id="save">` gets a Rust handler; it is not guarded by the enabled state (`ElementRef::effectively_enabled` is there to check).

Attribute-to-prop sync would loop (prop -> attribute -> `attributeChangedCallback` -> prop...) if `Prop::set` always applied; it skips equal values, which ends the loop.

## Data binding

moth's push model, no diffing. `Prop<T>` (`T: Clone + PartialEq`) holds a value and bindings that write the DOM directly; `bind` applies the current value immediately and lasts as long as the prop, `bind_scoped` returns a `Subscription` that removes the binding when dropped. A component uniquely owns its props and exposes `WeakProp<T>` handles (`label.text_handle()`, `image.source_handle()`...) for callbacks: `get` returns `None` and `set` returns `false` once the owner is gone, which is the dangling detection moth's `DataPool` never had. Props that carry an invariant do not hand out a raw `WeakProp`: `Slider::handle()` and `ProgressBar::handle()` clamp like their setters.

### Enabled

Every component has an `enabled` property (`Component::set_enabled`) that *is* the `disabled` attribute of its host: writing the attribute from anywhere (markup, a script, Rust) changes it, and changing it writes the attribute. That is the component's own state. The effective state is that and every ancestor being enabled, like WPF's `IsEnabled`:

- handlers (clicks, toggles, `input`/`change` of the controls) are guarded by the effective state **read from the DOM at the time of the event**, so they are right even when something moth cannot observe changed, such as a `<fieldset disabled>` toggled at runtime; a programmatic `host.click()` or a dispatched `input` is guarded too;
- the inner control (`<button>`, `<input>`...) and the submitted form value follow the effective state through events: an ancestor change notifies the light-DOM descendants (one event each, the ancestor check reads attributes), and a component recomputes when it connects, so moving an element between parents is handled. **Not observed:** a non-moth ancestor (a native `fieldset`) changing at runtime does not update the inner control's `disabled` or the form value until the component next connects or an ancestor moth component changes; the handler guard still blocks it.

CSS can target `moth-panel[disabled] moth-label` since the attribute stays the own state.

### Re-entrancy: run-to-completion

Both `Prop` and `Listener` queue instead of nesting:

- A `set` issued from inside a binding stores its value at once but is applied to the bindings after the running pass finishes. Bindings therefore receive values in order, and no `RefCell` borrow is held while user code runs. (A `get()` inside a binding already sees the newest stored value, which can be newer than the one that binding was handed.)
- `Listener` registers an `Fn` closure with wasm-bindgen (re-entering an `FnMut` one throws a JS error) and does its own `try_borrow_mut`; events that arrive while its callback runs are delivered afterwards, in order, unless the listener was dropped meanwhile.
- Not solved by design: a handler that `borrow_mut`s a user `RefCell` that is already borrowed further up the stack. That is ordinary Rust and stays the user's responsibility.

## Form controls

`Edit`, `Slider` and `Dropdown` are form-associated (`ElementInternals.setFormValue`): the value is submitted under the host's `name` with the enclosing light-DOM `<form>`, and nothing is submitted while the control or an ancestor is disabled (covered by `FormData` tests, ancestor case included). Dropping one removes it from the submission. `ProgressBar` is not a form control. `Slider` keeps its value within `min..=max` (an inverted range counts as `max = min`, like an HTML range input) and on the browser's step grid, so the property is always what the input displays and the form submits; markup numbers are parsed with HTML rules (`inf` and `NaN` are not numbers). `Dropdown` is Rust-only (its options come from Rust).

Text components (`Label`, the buttons) keep their text in a text node of their own, first among the children, so setting a text never touches child components added to the element.

## WebSocket

`WebSocket::connect(url, Handlers::new().on_open(..).on_message(..).on_error(..).on_close(..))`.

- Callbacks receive a `SocketHandle` argument, so they can answer without capturing the socket that owns them (which would be a cycle). Components created before the socket reach it through a slot filled afterwards (`Rc<OnceCell<SocketHandle>>` in the sample).
- Dropping the socket drops its listeners (RAII, through `Listener`) and closes it with code 1000. No callback runs afterwards; the test asserts that `on_close` and a frame handler stay silent and that the page reports no error. (The explicit `listeners.clear()` before `close()` only fixes the order; the browser never delivers events synchronously inside `close()`, so the order is not observable.) A callback may drop its own socket.
- `send_*` returns `Result` and is only attempted on an open socket. The browser silently discards data sent on a closing or closed socket; the C++ `Send` had an inverted success flag for the same kind of silent failure. A failure while attaching the listeners closes the socket instead of leaking it.
- Browser facts that bit during testing: `new WebSocket("not a url")` does not throw (relative URLs resolve against the page); an unreachable server gives `error` then `close` with `was_clean == false` (code 1006).

## Model replication (the "model + controller" of the original TODO)

The server owns the model; the page holds an empty shell and never edits it.

- **`Replica<M>`**: the client's copy, a `Prop<M>` underneath. `replica.bind(select, apply)` runs `apply` now and whenever the *selected field* changes, so a snapshot does not rewrite what did not change (`bind_scoped` for components that come and go).
- **`Link<M, A>`** (feature `replication`): a `WebSocket` whose text frames are, from the server, the complete model as JSON, and, from the client, an action as JSON (serde). `link.actions()` is a cloneable, non-owning `Actions<A>` for control callbacks; sending after the link is dropped or the connection lost is an `Err`. `LinkEvent` reports open, close, a pending reconnection and a frame that is not a valid model (the replica is then left alone). Dropping the link applies no further snapshot.
- **Reconnection** (`Link::connect_with` with `LinkOptions { reconnect: Some(Backoff) }`; off by default). After the connection ends the link waits (`Backoff`: 500 ms doubling to 10 s by default, each wait randomized by ±20% so clients that lost the same server do not return together, never 0) and opens a new socket; the attempt counter restarts after a connection that opened. The server sends the full model on every connection, so the first snapshot repairs whatever the page missed, and until then the page keeps showing its last model. `Actions` point at the link's *current* socket, so a sender taken before a reconnection keeps working; sending while disconnected is an `Err`. `link.reconnect()` abandons the current socket (silently) and reconnects now, with or without automatic reconnection. The timer is an RAII `Timeout` that dies with the link. A server that refuses the connection (a 403 for a foreign origin, say) is retried like one that is down, forever, at the maximum wait.
- **`Keyed<K, T>`**: `sync(parent, items, key, create, update)` makes the components match a list. A vanished key drops its component (element and listeners with it, this is where destructors earn their keep), a new key gets one, an existing key keeps its component and is updated. The rows form one contiguous block of the parent that ends at a marker node (an empty comment) the `Keyed` places at the end of the parent, or before a node given to `Keyed::before`; other children of the parent are left alone, before or after. It remembers the order it made and moves the minimum number of elements (a longest-increasing-subsequence pass; moving one row to the front moves one element), since a moved element loses focus and selection. Duplicate keys are refused and change nothing. Not atomic: vanished rows are dropped first, and if `create` fails the rows made so far stay and the next sync puts them in place. Use one parent per `Keyed` and do not reorder its elements by hand.
- The reducer (`Todos::apply`) lives in the shared `protocol` crate, is pure and is tested natively; it ignores invalid actions and caps the list (500 items, 200 characters per text, ids never reused or wrapped). The server serializes the model after each action into a `watch` channel, so every client gets the latest snapshot (shared bytes, not a copy each) and a slow one skips intermediate states. A new connection starts with the current model.
- Why snapshots and not deltas: simple, and self-healing (a missed frame is fixed by the next). Deltas are the follow-up if a model grows large enough to matter.
- **Controls and the model.** `ToggleButton::new` flips at once and reports; `ToggleButton::controlled` only *requests* (its callback gets the state it asks for) and changes when the owner calls `set_toggled`, so it can never disagree with the model; the todo rows use it. Without it a toggle can diverge even when the server refuses nothing, because snapshots are coalesced: two clients flipping the same item can leave a client whose final snapshot equals its previous model, so no binding runs and its locally flipped toggle stays wrong. `Edit`, `Slider` and `Dropdown` still show the user's input before any answer; for them the model is a mirror, not an arbiter.

## Canvas

`Canvas::new(parent, on_draw)`: the backing store follows the element's CSS size (a `ResizeObserver`) and the device pixel ratio, and the callback draws in CSS pixels on an already scaled context. `invalidate()` requests a redraw, coalesced to one per animation frame; the callback may request the next frame (an animation loop). Dropping it cancels the pending frame, disconnects the observer and removes the pixel-ratio listener, also when dropped from inside its own callback. The `<canvas>` is positioned out of flow so its backing size can never feed back into the host's size. Real pixels are read back in the tests and in the todo end-to-end run.

The pixel ratio can change without the element's CSS size changing (a window moved to another monitor, zoom), which a `ResizeObserver` does not report. The canvas listens to a `(resolution: Xdppx)` media query for the current ratio and re-arms one for the new ratio each time it fires (the documented technique, e.g. MDN "Monitoring screen resolution or zoom level changes"). **What is verified and what is not:** the tests (`canvas_dpr.rs`) replace `matchMedia` and `devicePixelRatio` and check moth's side (which queries it registers, that a change rescales and re-arms, that only one listener is live and none after the drop). Whether the browser delivers the event for a real change was *not* observed: DevTools emulation (`Emulation.setDeviceMetricsOverride`) changes `devicePixelRatio` but Edge then does not notify an existing resolution query, so it cannot exercise this path.

## Server (sample back-end)

Single port (the original used two): `/ws`, `/todo/ws` and `/viewer/ws` plus the static builds. Options: `--port`, `--bind`, `--dir`, `--todo-dir`, `--viewer-dir`, `--allow-origin ORIGIN` (repeatable), `--dev`.

- **Origin policy.** A browser lets any page open a WebSocket to any address, so a page the user has open could drive this server (cross-site WebSocket hijacking). Upgrades are accepted from the server's own origin, from `--allow-origin` origins, and with `--dev` from any page served by a loopback host (a `trunk serve` page, the wasm test runner, whose origin has a random port); requests with no `Origin` (not a browser) are accepted; anything else gets 403. `Origin: null` is only accepted if named. The sample pages connect to their own origin by default, or to `?backend=host:port` (e.g. a page from `trunk serve` with the back-end run with `--dev`), over `wss` when the page is `https`.
- **Limits.** Messages and frames over 16 KiB are refused by the WebSocket layer and end the connection; the model is capped. Not done: idle or write timeouts, a limit on connections. Client text is logged escaped.
- The stream is per connection (the Node runner had one global timer for all clients). Each connection's writer task closes its sink on exit: without that a client-initiated close is never answered and the browser reports an abnormal 1006 closure (a test caught this). The log says whether a connection ended `clean` or by `connection lost`.

## 3D viewer

`samples/viewer` is the "server-side streaming" showcase: the server renders a 3D object and sends pictures; the page steers it. It is built from stock components (`Panel`, `Label`, `Dropdown`, `Slider`, `ToggleButton`, `PushButton`, `Canvas`) and `Link`; `LinkEvent::Binary` was added to the library so that binary frames reach the application next to the replicated model (the hub: the shared scene, the list of models and the number of viewers, as JSON snapshots on the same socket).

**One server, one scene (a decision).** Everyone connected to a server shares one `Scene` (model, material, camera, light, shininess, wireframe, turntable): it lives on the server, like the todo list, and every browser shows it. Independent sessions are separate servers on other ports, not rooms or session ids inside one: the user preferred that to anything to manage. What belongs to one browser alone is a `Display` (its frame size, its resolution, how big its previews are while the scene moves, and the JPEG quality of the full frame and of the previews) and is not shared. A restarted server starts from the default scene and the pages adopt it (the scene is not persisted).

**Renderer** (`samples/render`, native, no dependency on the web crates): a software rasterizer, multi-threaded in horizontal bands, Blinn-Phong shading, optional wireframe, supersampling; the meshes are generated (torus knot, torus, sphere, gem) and tested to be closed and consistently wound (the first torus knot was wound inward and the gem had cracks: the tests now report every mesh). It exists so the sample needs no GPU, no native library and nothing outside `cargo`.

**Protocol** (`samples/protocol/src/viewer.rs`, shared by both sides). Client to server, JSON: `Set(Patch)` changes the scene, `Display` tells the server this browser's frame size and quality, `Ack` acknowledges a frame. Server to client: the `Hub` (with the `Scene`) as a text snapshot, and binary frames: a 26-byte little-endian header (`MOTH`, sequence, view id, kind, width, height, render and encode time in microseconds) then a JPEG.

**Concurrent editing.** A `Patch` holds only the fields that change (`Option`s), so two clients changing different things at once both win; for the same field the later patch wins (the server applies them in arrival order under one lock). `Scene::apply` bounds every number (a non-number is ignored), and a patch that changes nothing is not published, so a client that re-sends what it already shows costs the others nothing. The scene carries who changed it last (`author`, the client id a patch names, and that client's `seq`; author 0 is the server's turntable), which is how a client tells the echo of its own older edits from news (`samples/viewer/src/outbox.rs`, pure and tested natively):

- an echo of an edit superseded by a newer one already sent is not shown, and neither is an echo of its own while something is waiting to be sent: either would pull the camera back while the user is still dragging it;
- anything else is shown: another viewer's change, the turntable's, and the echo of its own newest edit, which also settles races (the client that lost a same-field race ends up showing the server's winner);
- on a new connection the page forgets what it had to say and takes the server's scene as the truth.

The controls follow the scene (setting a control from code never calls its callback, so no loop back to the server). The toggles are `ToggleButton::controlled`: a click is a request and the button shows what the server then announces, so it cannot disagree with the model.

**The turntable is the server's.** While `spin` is on and somebody watches, a task advances the camera every 16 ms by the real elapsed time and publishes it (author 0); it stops by itself when the turntable is switched off or the last viewer leaves, and restarts for the next one. A client that spun its own camera would fight the others. Cost: with auto-rotate every viewer is streamed continuously, which is what the shared rendering below is for.

**Flow control**, per connection; four rules, each with a test:

- *Latest wins.* Whenever the renderer has something to do it looks at the newest picture (the scene as it is now, with each viewer's display): states that came and went while it was rendering are never drawn, so a burst of 60 changes produces a handful of frames, the last one from the newest state (checked by the raw-protocol end-to-end run). A frame is delivered even if the state has moved on meanwhile, otherwise a turntable turning faster than the renderer draws would starve everyone.
- *Credits.* At most `FRAMES_IN_FLIGHT` (2) frames are unacknowledged; the page acks every frame, including those it no longer shows (a superseded frame is acked at once). Acks that do not match a frame in flight are ignored, so a client cannot raise its own limit (200 unearned acks change nothing). A slow client skips frames; it never slows the others, whose credits are their own.
- *Progressive refinement.* While the picture keeps changing, previews (by default half the full frame's size, no supersampling, JPEG quality 60); how big the previews are (a tenth to the whole frame) and the JPEG quality of previews and of the full frame (10 to 100; 60 and 90 by default) are each viewer's choice, four sliders in two cards ("At rest", "While moving"), so that sharpness can be traded for bandwidth separately for a picture at rest and a picture in motion; after `SETTLE` (220 ms) without a change, one final frame (full size, 2x supersampling, quality 90). A viewer that is new or has just resized starts with a preview too (the picture has just changed for it), while one that was held back by its credits and comes back to a picture that has rested is sent the full frame straight away. A change that alters nothing visible (a viewer joining, a no-op patch, the turntable's switch) renders nothing.
- *Untrusted input.* `Scene::apply` and `Display::sanitized` bound everything (a size beyond the biggest frame, 1280x720, is shrunk on both sides alike, see the gotcha below); a malformed message is ignored (and logged); the 16 KiB message cap and the origin policy apply as for the other endpoints. Not done: a rate limit, so a client sending patches as fast as it can makes the server serialize and publish each one (the renderers still only see the newest).

**Shared rendering** (`samples/back-end/src/share.rs`, the scheduler in `viewer.rs`). One task renders for all the viewers, instead of one per connection. Each viewer asks for a frame of some size (its canvas times its resolution setting, halved for a preview), and the plan is, from the biggest viewer down:

- viewers of the same shape (aspect ratios within 3%: a picture can be scaled but not reshaped without distorting it) are served from one **rendering** at the size of the biggest;
- a viewer at least 85% as wide as an output takes that output as it is (the browser scales it to its canvas), so near sizes share even the compression, and viewers of the very same size are sent the very same bytes (each connection only writes its own 26-byte header: its sequence number, and whether the change shown was its own);
- one at least 40% as wide as the rendering gets a copy **reduced on the server before it is compressed** (`Image::resized`, an area-averaging box filter in the render crate); reduced sizes are shared among viewers near each other in the same way;
- a picture is shared only by viewers who want the same JPEG quality: the rendering is shared all the same (viewers of one screen at qualities 20, 90 and 100 are served by one rendering and three compressions), and each quality is compressed on its own;
- a smaller one, or one of another shape, starts a rendering of its own: rendering small is cheaper than reducing from big. In between ("really too divergent") is therefore a fall-back to several renderings.

The grouping is pure arithmetic over sizes (`share::plan`) and is tested on its own, including that every viewer is served exactly once whatever the sizes. Credits and the settle timer stay per viewer, so a slow viewer skips frames without affecting anybody; a viewer that is behind is sent the newest state when it has room. The cost of a picture now depends on how many *different* screens there are, not how many viewers: the end-to-end run shows four viewers (two the same, one half size of the same shape, one of another shape) costing two renderings per kind of frame, and two browsers of the same size reporting the same render and encode time in their HUDs.

*Limit:* viewers share a rendering only when they want a frame at the same moment. A change of the scene wakes everybody at once, so from the first change on it works; but viewers that *arrive* a few milliseconds apart are each rendered for as they come (their messages are separate and the renderer does not wait), and their full frames are due a few milliseconds apart too. A short gathering delay for new displays would align them; it was not added.

**Camera on the client.** `orbit.rs` is plain arithmetic (drag, exponential zoom, pitch clamped before the poles, non-finite input ignored), tested natively. The page sends at most one patch per animation frame, with the camera position of that moment. Frames are decoded with `createImageBitmap` from a `Blob` and drawn on the `Canvas`; the HUD (frames/s, latency, frame kind, size, server render and encode time, a sparkline) is computed from the frame headers (`stats.rs`, native tests). A frame's header names the patch it shows only to the browser that sent it (else 0), so the round trip shown is that of the user's own moves.

**What was measured** (loopback, this machine, dev build of the server except the renderer and the JPEG encoder, which are always optimized): a final 1030x686 frame is ~15 ms of rendering plus ~6 ms of encoding, ~25 kB; the turntable streams ~60 frames/s to each of two browsers at once; dragging gives ~13 previews/s in headless Edge. Loopback has no bandwidth limit, so these numbers say nothing about a real network. The credits are what should make the stream degrade gracefully there, but that was not tested over a throttled link.

**Gotchas found on the way:**

- *Generics are compiled in the caller's crate.* `jpeg-encoder` called from the server crate (unoptimized in dev) took 30 ms per frame; wrapped in `moth_sample_render::encode_jpeg` (the render crate and `jpeg-encoder` are optimized in the dev profile) it takes ~6 ms. 4:2:0 chroma subsampling is another ~40% faster and smaller.
- *Release profiles.* The workspace's release profile is for wasm (`opt-level = "s"`, `panic = "abort"`). The native server is meant to use `--profile server` (inherits release, `opt-level = 3`, unwinding). `cargo build --profile server -p moth-sample-back-end` builds (33 s from clean dependencies); the server was not otherwise run from that build.
- *WebDriver and range inputs.* Headless Chromium driven through WebDriver does not apply Home/arrow keys to `<input type=range>`, not even a plain one outside moth; the end-to-end run moves the sliders with real pointer clicks on the track.
- *.NET `ClientWebSocket`* (the raw PowerShell client) aborts the socket if a pending receive is cancelled, so the harness waits for the pending task instead.
- *A frame must have the shape of the canvas it is drawn on.* The page stretches each frame to its canvas, so a frame of another shape looks distorted. Clamping the requested width and height each to the biggest frame did exactly that to tall and very wide windows (a 489x841 canvas was sent a 489x720 frame: a sphere came out 43% too tall); `Display::sanitized` now shrinks both sides by the same factor. A second effect of tall pictures was found by looking at one: the camera's field of view was fixed on the vertical axis, so in a narrow window the object was wider than the picture and cut off at the sides; the field of view is now that of the shorter side, which keeps an object the same size in a square, a tall and a wide picture of the same short side. Both are tested natively (shape kept for many sizes; a sphere round and uncut in five shapes), and the end-to-end run opens a tall and a very wide window, checks that the frame has the canvas's shape and that the sphere on the canvas is round and fits. With the old clamp those checks fail (measured: the sphere 489x699 pixels).
- *The end-to-end harness had two weaknesses, found when a run printed "passed" after skipping the whole page section.* A fresh front-end build makes the first page load slow (the WebAssembly is compiled), and a check made before the page had built its elements got a JavaScript error, which in PowerShell stops the `try` block but lets the script go on to its summary. The scripts now catch such an error, print FAIL and exit non-zero, and `Wait-For` treats an error in its condition as "not yet". Also: a range input's thumb covers the end of its track, so a click "near the right end" can land on it and move nothing; the script computes the click position for a value instead of guessing a fraction.
- *A scene that is shared is also shared with the tests.* The end-to-end script's raw clients change the one scene the page then loads, so it puts the scene back to its defaults between sections.

**How it was checked.** Native tests: renderer 27 (incl. the resize: flat colours stay exact, averages, shape and brightness of a render kept; a sphere round and uncut in five picture shapes), protocol 23 (patch merging and bounds, no-op patches, the turntable's arithmetic, display bounds, shape, preview size and JPEG qualities, wire formats), server 45 (the hub: one scene for all subscribers, no-op patches not published, hostile patches bounded, the turntable for everyone; the scheduler with real subscriptions: preview then full frame then silence, identical frames for equal screens, a smaller viewer from the same rendering, another shape rendered separately, a slow viewer never holding up another and getting the newest state when it acknowledges, a burst of changes, a resize, a viewer choosing the size of its previews, the JPEG quality of each kind of frame, the renderer stopping and restarting; the grouping rules in `share.rs`, including a randomized check), viewer 20 (camera, statistics, the echo rules of the outbox). `scripts/e2e-viewer.ps1` has four parts. Raw client (`scripts/viewer-client.ps1`): preview then final frame, a 60-change burst, the two-frame limit, unearned acks, hostile sizes and patches, malformed messages, viewer count, foreign origin, an oversized message. Shared scene, two or three raw clients: a change reaches the other and is streamed to it at its own size, different fields merge, the later change wins on the same field, a no-op is silent, a late viewer is sent the scene as it stands, the turntable turns for both and one can stop it, the scene outlives its viewers. Shared rendering, four raw clients: the same screen gets byte-identical frames with identical render and encode times, a half-size screen of the same shape gets its own smaller file from the same rendering, another shape gets a rendering of its own. Browsers (headless Edge, real input): drag, wheel, menu, slider and toggle clicks change the picture; a second browser opens on the first's scene, follows it (menu, sliders, toggles, picture) and steers it (its drag turns the first browser's object, its turntable spins both), keeps its own resolution, and follows a raw client too (the moving resolution slider changes the size of the previews it receives while dragging, the two JPEG quality sliders the weight of the full frame and of the previews, and a raw client can ask for any preview size and quality, bounded; raw clients of one screen at qualities 20, 90 and 100 are served by one rendering and get files of increasing size); a third, as big as the first, reports the very same frame in its HUD while the smaller window is rendered separately; a tall and a very wide window get frames of their canvas's shape and a round, uncut sphere; a killed and restarted server is recovered from with the scene back at its defaults. Mutation checks: removing the credit limit makes a native test and two end-to-end checks fail; believing every echo (outbox), publishing no-op patches, treating no two shapes as alike and reducing from any size however small each fail native tests.

## How the tests were checked

- `scripts/test-wasm.ps1`: builds and starts the back-end (refusing to if port 2000 is taken, instead of silently testing a stale server) and runs `cargo test -p moth --all-features` in headless Edge. 183 wasm tests (9 of them for the guides, see "Documentation and the starting project"), plus 115 native (`protocol` reducer, wire formats and the shared viewer scene, the renderer, the back-end's origin policy, viewer hub, scheduler and sharing rules, the viewer's camera, statistics and echo rules).
- `scripts/e2e.ps1` / `scripts/e2e-todo.ps1` / `scripts/e2e-viewer.ps1` (see "3D viewer"): real clicks and typing through WebDriver; the second uses two browsers on one server and checks sync, ordering, canvas pixels, reload catch-up, the origin policy and size limit with a raw client, that a page torn down by `pagehide` closes its socket cleanly, and that the pages survive the server being killed and restarted (they keep their last model, say they are retrying, reconnect by themselves, and the new server's snapshot replaces the stale list).
- **Mutation checks.** A test that cannot fail proves nothing, and several could not (see the audit below). For the unregistration paths, the corresponding line was removed and the test confirmed to fail, then restored: `Listener::drop`'s `removeEventListener` (lifecycle and WebSocket tests), the `closed` flag (queued-event test), `Canvas`'s frame cancellation, the pixel-ratio watcher's three steps, `Keyed`'s reordering and minimal-move logic, `Timeout`'s `clearTimeout` (timer and link tests), the `persisted` check on `pageshow`, the `composed` flag of emitted events, the order of the toggle event and its callback, and the README's verbatim check (one character changed in a snippet). The checks are manual, not part of the suite.
- **The README is tested.** Each of its examples is a file in `moth/tests/readme/`; `moth/tests/readme.rs` compiles and runs them in the browser and fails if `README.md` stops containing any of them verbatim.
- Test gotchas: `HTMLElement.click()` is a no-op while a click is in progress on the same element (HTML spec), so re-entrancy tests use `dispatch_event`; calling a dropped wasm-bindgen closure only *reports* an error on the page, so such tests also assert `ErrorWatch::assert_none()`; wasm-bindgen-test appears to run `async` tests concurrently, so tests sharing state key it per test.

## The two independent audits

Two reviewers (Opus and Fable, independent briefs, read-only, no hypotheses supplied) audited the project at the end of phase 4. They agreed on most findings; every browser-dependent one was first reproduced with a failing test, then fixed. Disposition:

- **Fixed, found by both:** markup left inert if a Rust constructor defined its tag first; form controls disabled through an ancestor still submitted; no `Origin` check or size/count limits on the server; `pagehide` tearing down a bfcache page; `Keyed` misplacing siblings after the rows and moving more than needed; stale effective-enabled after a move and an ignored external `disabled` on Rust-created hosts; the canvas ignoring pixel-ratio changes; the `Listener` delivering queued events after it was dropped; `test-wasm.ps1` not checking its server bound the port.
- **Fixed, found by one:** `set_text` wiping child components; `value_handle()` bypassing clamping; slider prop/display disagreement under a step; `inf`/`NaN` accepted in markup; a component moving its own element while attaching; bindings that could not be removed; markup components not dropped on `pagehide`; programmatic `input` on a disabled control; two `Host`s on one element through `Anchor` (now `ElementRef`); the Add button discarding input after a failed send; `next_id` wrap; the WebSocket constructor leaking a socket; a tag silently swapped between component types; hard-coded `ws://:2000` URLs; unescaped client text in the server log; toggles diverging under coalesced snapshots (now `controlled`).
- **Worse than reported:** an `attach` that moves its own element did not merely create a second instance: the confirmation test counted 43 attaches, a runaway recursion. It ended on its own; why it stopped at that depth is the browser's doing and was not investigated.
- **A finding that did not reproduce as described:** a queued event delivered after a drop did not show through `PushButton`, whose click guard goes through a weak handle that was already dead; it was real at the `Listener` level and is tested there.
- **A premise that was wrong:** the audit said the WebSocket drop test would pass without `listeners.clear()`. True, but the line is redundant (the field drops right after), so removing it changes nothing; the test *was* too weak, for a different reason (the browser stops delivering `message` events once `close()` is called), and now checks `on_close` and uncaught errors.
- **Documented, not fixed:** a non-moth ancestor changing at runtime does not update the inner control or form value (the handler guard is correct); `Keyed::sync` is not atomic; the controls other than the controlled toggle show input before the model answers; no idle/write timeouts or connection limit on the server. (The audit also listed the missing reconnection; `Link` has it now, see "Model replication".)

## Documentation and the starting project

What a stranger finds, as of the docs and packaging pass:

- **API reference.** Every public item of `moth` has rustdoc, and `#![warn(missing_docs)]` keeps it so; `RUSTDOCFLAGS="-D warnings" cargo doc -p moth --all-features` is clean. The crate docs (`moth/src/lib.rs`) give a first page and a map of the API. The doc example is `no_run` (it compiles when `cargo test --doc` is run on the host; the wasm test runner does not run doc tests), and the README's example is the one that is run.
- **Guides** in `docs/`: getting started (with a table of the first problems), a tutorial that builds a shopping list, writing components (compose / a new element / an element for markup), styling (variables, parts, what does not work). The code in them is files that the test suite compiles and runs (`moth/tests/guides.rs`, `moth/tests/guides/*`, and the starting project): each guide must contain its files verbatim, and the tutorial, which walks through one program in excerpts, must show every line of it. The styling guide's claims (variables reach the inside, `::part()` reaches what they do not, page CSS naming an inner element does not) are checked against computed styles. Corrupting a guide, or the theme, makes these tests fail (checked).
- **Starting project** `templates/hello`: excluded from the workspace so that it can be copied out and built alone. Built and run in a browser from a cold start (35 s): it counts clicks and takes its look from `style.css`.
- **`moth::init()`** installs a panic hook that writes the message, file and line to the console, without a dependency (`console_error_panic_hook` was in each sample; they use `init` now).
- **Component authoring.** `Definition::create` and `Host::shadow` were `pub(crate)`: a component with its own template and styles could not be written outside the crate, only composed, or defined for markup. They are public now, with the guide's `Meter` as the tested example. Still not possible for a component of your own: submitting a value with a form (`form_associated` is honoured, the call that sets the value is not public).
- **Packaging.** `LICENSE-MIT` and `LICENSE-APACHE` (the standard texts; copyright held by Arnaud SINTES, the owner's choice of licence and holder, confirmed before the repository was published), `license`, `keywords`, `categories` and `rust-version` in `moth/Cargo.toml`. `rust-version` is the toolchain it is built with (1.98), not a measured minimum.
- **Found while writing it:** `Slider::set_min`, `set_max` and `set_step` do not validate their argument (documented as such); a markup `text` attribute that is removed leaves a `Label` or `PushButton` showing the old text, whereas `Edit` and `Image` reset (probably unintended, not changed). The tests for the guides tripped over the very thing the getting-started guide warns about (`Document::head` needs a `web-sys` feature).

## Known risks

- **Closure dropped during its own invocation** (a "delete this row" button): wasm-bindgen defers the free until the call returns. The tests check what is observable (no crash, no further calls), not memory safety itself; the evidence for that is wasm-bindgen's design.
- **Shadow DOM vs global CSS** (see above).
- **Process-wide registries:** declarative components keep one thread-local registry of factories and instances and one global hook. Fine for a page. Two copies of the wasm module on one page would not each define their tags: the second copy would bind to the first copy's element classes and hook, and its `define` would not instantiate anything.
- **Engines:** Chromium only (see the top). The tests also depend on Chromium behaviours: e.g. a closing socket delivers no `message` events, a dropped closure's call is only *reported* on the page, `HTMLElement.click()` is a no-op during a click.
- **Size** (release build, `trunk build --release`, which runs binaryen's `wasm-opt`; measured before the audit fixes, not a budget): streaming sample 163 KB wasm (76 KB gzipped) + 32 KB JS glue; todo sample 131 KB wasm (57 KB gzipped) + 37 KB JS glue. Both include serde_json. The glue is generated by wasm-bindgen.
- **Prior art.** Leptos, Sycamore, Yew and Dioxus exist; none was assessed in depth. moth2's differentiator is the ownership tree and Qt/WPF feel, not novelty of fine-grained updates.

## Dev setup

```
rustup target add wasm32-unknown-unknown
cargo install trunk --locked
cd samples/front-end && trunk build        # and the same in samples/todo and samples/viewer
cargo run -p moth-sample-back-end          # http://127.0.0.1:2000/  /todo/  /viewer/  (open /todo/ in two tabs)
```

For a page served by `trunk serve` instead, run the back-end with `--dev` and open the page with `?backend=127.0.0.1:2000`.

Tests need a WebDriver matching your browser (`msedgedriver` / `chromedriver` / `geckodriver` on `PATH`, or `MSEDGEDRIVER` & co.). `.cargo/config.toml` already sets `wasm-bindgen-test-runner` as the wasm runner:

```
cargo install wasm-bindgen-cli --version <same as the wasm-bindgen crate in Cargo.lock> --locked
.\scripts\test-wasm.ps1     # builds + starts the back-end (--dev), runs `cargo test -p moth --all-features`
.\scripts\e2e.ps1           # trunk build + back-end + headless Edge driving the streaming sample
.\scripts\e2e-todo.ps1      # same for the todo sample, with two browsers on one server
.\scripts\e2e-viewer.ps1    # the viewer: raw protocol checks, then browsers (-NoBuild, -Quick, -Screenshots <dir>)
cargo test -p moth-sample-protocol -p moth-sample-render -p moth-sample-back-end -p moth-sample-viewer      # native
```

Which to run: `e2e-viewer.ps1 -Quick` (about 70 s here, 88 checks) after a change to the viewer's page, settings or protocol; the full run (about 105 s, 135 checks) after a change to the server's rendering, sharing or the shared scene, and before calling a viewer change done; `-Quick` leaves out the viewers-with-alike-screens checks, the second and third browsers and windows of other shapes, and the killed and restarted server. The scripts print how far into the run each section starts. Measured by timing a run: the cost is spread over many short waits (about 45 settle checks and 40 raw-client "nothing more arrives" windows), which is why they were shortened (settle poll 700 to 350 ms, quiet window at most 800 ms) rather than any one step being slow.

`scripts/webdriver.ps1` is the small WebDriver client and back-end launcher the scripts share; `scripts/viewer-client.ps1` is the raw viewer-protocol client. The workspace's default members exclude the native-only back-end, so wasm commands must name their package (`-p moth`).
